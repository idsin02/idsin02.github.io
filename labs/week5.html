How Week 5 works

Week goal

Alert when one source IP and device fails authentication for at least five distinct accounts inside five minutes.

A true spray is wide: one source → many usernames. Repeated failures for one username are not enough.

Telemetry to keep

  • Source IP and source device
  • Account or username
  • Result: failure or success
  • Logon type
  • Precise timestamp

Week 5 · Day 2

KQL behavior query + tuning

Page 3 / 8

Build it in five steps

  1. Read IdentityLogonEvents.
  2. Keep failed logons.
  3. Remove the documented scanner and password-sync device.
  4. Group into easy five-minute buckets.
  5. Require at least five distinct accounts.

Beginner note

This KQL uses fixed five-minute buckets so it is easy to read. A production rule can run frequently with an overlapping lookback. Day 5 demonstrates a true sliding window.

Only tune a scanner or connector after confirming its owner, purpose, and expected source.

KQL answer

Field names match Microsoft Defender's identity table. Validate them in your tenant before production use.

let Window = 5m;
let AccountThreshold = 5;
let KnownScanners = dynamic(["10.10.5.20"]);
IdentityLogonEvents
| where Timestamp > ago(1d)
| where ActionType == "LogonFailed"
| where IPAddress !in (KnownScanners)
| where DeviceName !in~ ("password-sync-01")
| summarize
    FailedEvents = count(),
    DistinctAccounts = dcount(AccountUpn),
    Accounts = make_set(AccountUpn, 25),
    FirstSeen = min(Timestamp),
    LastSeen = max(Timestamp)
  by IPAddress, DeviceName, bin(Timestamp, Window)
| where DistinctAccounts >= AccountThreshold
| project FirstSeen, LastSeen, IPAddress, DeviceName,
          FailedEvents, DistinctAccounts, Accounts
| order by DistinctAccounts desc

Analyst reasoning

The rule looks for account breadth, not just volume. False positives can include vulnerability scanners, many users behind a shared proxy, a broken SSO connector, and password-sync systems. Confirm ownership and source stability before allowlisting. Shared proxies should usually receive a higher threshold instead of a broad exclusion.

Validation status

Not executed: KQL needs a live Microsoft Defender tenant. The fixture validator on Day 7 tests the same threshold and tuning idea locally.

CrowdStrike CQL answer

Falcon field names vary by connector and data source, so confirm this map against your own events.

#event_simpleName=UserLogonFailed2
| RemoteAddressIP4!="10.10.5.20"
| ComputerName!="password-sync-01"
| groupBy([RemoteAddressIP4, ComputerName], function=[
    count(as=failed_events),
    count(field=UserName, distinct=true, as=distinct_accounts),
    collect([UserName], limit=25)
  ], limit=max)
| distinct_accounts>=5
| sort(distinct_accounts, order=desc)

Analyst reasoning

Use the five-minute search range as the time window. Investigate whether the IP is external, whether the device value is expected, and whether any failure is followed by success. False positives include vulnerability scanners, shared proxies, broken SSO connectors, and password-sync systems.

What this rule does

The Sigma rule selects Windows failed-logon events and removes two documented sources. It intentionally stays simple. Counting five different usernames in five minutes is a SIEM correlation step.

Week 5 · Day 5

Python sliding-window test

Page 6 / 8

What the code does

  1. Reads events.jsonl one line at a time.
  2. Keeps failures and removes two known benign sources.
  3. Groups rows by source IP and device.
  4. Slides a five-minute window over each group.
  5. Prints a breach at five different usernames.

Expected result

Only 198.51.100.45 / web-gateway-02 and 203.0.113.77 / unknown-linux should print.

The repeated alice failures do not alert because they are one distinct account.

Python answer

import json
from collections import defaultdict
from datetime import datetime, timedelta

WINDOW = timedelta(minutes=5)
THRESHOLD = 5
KNOWN_SCANNERS = {"10.10.5.20"}
IGNORED_DEVICES = {"password-sync-01"}

def parse_time(value):
    return datetime.fromisoformat(value.replace("Z", "+00:00"))

groups = defaultdict(list)
with open("events.jsonl", encoding="utf-8") as handle:
    for line in handle:
        event = json.loads(line)
        if event["result"] != "failure":
            continue
        if event["source_ip"] in KNOWN_SCANNERS:
            continue
        if event["device"] in IGNORED_DEVICES:
            continue
        key = (event["source_ip"], event["device"])
        groups[key].append(event)

for (source_ip, device), rows in groups.items():
    rows.sort(key=lambda row: row["timestamp"])
    for start, first in enumerate(rows):
        first_time = parse_time(first["timestamp"])
        window = [
            row for row in rows[start:]
            if parse_time(row["timestamp"]) - first_time <= WINDOW
        ]
        accounts = sorted({row["account"] for row in window})
        if len(accounts) >= THRESHOLD:
            print(
                f"BREACH {source_ip} / {device}: {len(accounts)} accounts "
                f"{first['timestamp']} → {window[-1]['timestamp']}"
            )
            break

Analyst reasoning

Python uses a real sliding window, so a burst crossing a fixed clock boundary can still be found. False positives remain possible from vulnerability scanners, shared proxies, broken SSO connectors, and password sync; exclusions should be reviewed and time-limited.

Validation status

Executed locally: the script returned exactly the two expected malicious sources and no benign source.

Week 5 · Day 6

Go failure aggregation

Page 7 / 8

What the code does

  1. Scans events.jsonl.
  2. Skips non-failures and the two narrow exclusions.
  3. Puts each event in a five-minute bucket.
  4. Stores usernames in a set.
  5. Prints buckets with at least five usernames.

Beginner note

The Go version uses fixed five-minute buckets to keep the code short. The Python version is the exact sliding-window reference for this test data.

For production, run overlapping queries or implement the same sliding logic as Python.

Go answer

package main

import (
    "bufio"
    "encoding/json"
    "fmt"
    "os"
    "sort"
    "time"
)

type Event struct {
    Timestamp string `json:"timestamp"`
    SourceIP  string `json:"source_ip"`
    Device    string `json:"device"`
    Account   string `json:"account"`
    Result    string `json:"result"`
}

type Group struct {
    Accounts map[string]bool
    Count    int
}

func main() {
    file, err := os.Open("events.jsonl")
    if err != nil { panic(err) }
    defer file.Close()

    groups := map[string]*Group{}
    scanner := bufio.NewScanner(file)
    for scanner.Scan() {
        var event Event
        if err := json.Unmarshal(scanner.Bytes(), &event); err != nil { panic(err) }
        if event.Result != "failure" || event.SourceIP == "10.10.5.20" || event.Device == "password-sync-01" { continue }

        parsed, err := time.Parse(time.RFC3339, event.Timestamp)
        if err != nil { panic(err) }
        bucket := parsed.Truncate(5 * time.Minute).Format(time.RFC3339)
        key := event.SourceIP + " | " + event.Device + " | " + bucket
        if groups[key] == nil { groups[key] = &Group{Accounts: map[string]bool{}} }
        groups[key].Count++
        groups[key].Accounts[event.Account] = true
    }
    if err := scanner.Err(); err != nil { panic(err) }

    keys := make([]string, 0, len(groups))
    for key := range groups { keys = append(keys, key) }
    sort.Strings(keys)
    for _, key := range keys {
        group := groups[key]
        if len(group.Accounts) >= 5 {
            fmt.Printf("BREACH %s → %d accounts in %d failures\n", key, len(group.Accounts), group.Count)
        }
    }
}

Analyst reasoning

Sets count each username once even if it fails repeatedly. That reduces noise from a broken connector. False positives still include scanners, shared proxies, SSO connectors, and password sync, so review the source and account types.

Why event count alone is insufficient

A broken SSO connector can create hundreds of failures for one account. That is a high event count, but it is not the wide account pattern of password spraying. Counting distinct usernames separates repetition from breadth.

Do not alert only because count() ≥ 5. Require distinct accounts ≥ 5.

Tune known scanners safely

  1. Confirm the scanner owner and ticket.
  2. Match the exact source IP or device.
  3. Record an expiry or review date.
  4. Keep unusual sources and changed identities visible.

Analyst reasoning

Prioritize unknown external sources, unmanaged devices, and a later successful logon. False positives: vulnerability scanners may test many identities; shared proxies combine many users behind one IP; broken SSO connectors can retry failures; password sync can touch many accounts. Tune with exact, owned infrastructure evidence. Raise the threshold for a busy shared proxy rather than hiding it.
