Week goal

Identify a success for the same account and source after at least three failures in ten minutes, then require useful success context: Network or RemoteInteractive logon.

Expected detections: sequences S1 and S2 only.

Simple detection contract

  2. Group by account + source.
  3. Keep failures for ten minutes.
  4. On success, require at least three failures.
  5. Require Network or RemoteInteractive context.

Week 6 · Day 2

KQL behavior query + tuning

Page 3 / 8

What should be done

  1. Build separate 4625 failure and 4624 success sets.
  2. Normalize account and source.
  3. Join on the same account + source.
  4. Keep failures in the ten minutes before success.
  5. Require three failures and logon type 3 or 10.

Easy tuning

Machine accounts, loopback addresses, empty sources, and known tightly scoped service-account/VPN pairs can create noise. Do not suppress an entire VPN range only because it is busy.

Logon type 3 = Network. Logon type 10 = RemoteInteractive. Confirm event-field mapping in your Sentinel workspace.

KQL answer

Use with the Windows SecurityEvent table. The panel contains code only.

let Window = 10m;
let FailureThreshold = 3;
let Failures = SecurityEvent
| where EventID == 4625
| where TargetUserName !endswith "$"
| where isnotempty(IpAddress) and IpAddress !in ("-", "127.0.0.1", "::1")
| project Account = tolower(TargetUserName), Source = IpAddress,
          FailureTime = TimeGenerated;
let Successes = SecurityEvent
| where EventID == 4624
| where LogonType in (3, 10)
| where TargetUserName !endswith "$"
| where isnotempty(IpAddress) and IpAddress !in ("-", "127.0.0.1", "::1")
| project Account = tolower(TargetUserName), Source = IpAddress,
          SuccessTime = TimeGenerated, LogonType, Computer;
Successes
| join kind=inner Failures on Account, Source
| where FailureTime between (SuccessTime - Window .. SuccessTime)
| summarize FailureCount = count(), FirstFailure = min(FailureTime),
            LastFailure = max(FailureTime)
    by Account, Source, SuccessTime, LogonType, Computer
| where FailureCount >= FailureThreshold
| project SuccessTime, Account, Source, LogonType, Computer,
          FailureCount, FirstFailure, LastFailure
| order by SuccessTime desc

Analyst reasoning

Likely false positives: users correcting passwords, mobile mail clients retrying stale secrets, cached credentials, and VPN retries. Confirm whether the source is known, whether logon type matches the user's normal behavior, whether MFA was involved, and whether the success reached a sensitive host. Event count alone is not proof of compromise.

#event_simpleName=/^(UserLogonFailed2|UserLogon)$/
| UserName!="" and RemoteAddressIP4!=""
| case {
    #event_simpleName=UserLogonFailed2
      | failure:=1 | success:=0 | failure_time:=@timestamp;
    #event_simpleName=UserLogon and LogonType=/^(3|10)$/
      | failure:=0 | success:=1 | success_time:=@timestamp;
  }
| groupBy([UserName, RemoteAddressIP4], function=[
    sum(failure, as=failure_count),
    sum(success, as=success_count),
    max(failure_time, as=last_failure),
    min(success_time, as=first_success)
  ])
| test(failure_count>=3 and success_count>=1)
| test(first_success>=last_failure)
| test(first_success-last_failure<=600000)
| table([UserName, RemoteAddressIP4, failure_count,
         last_failure, first_success])

Analyst reasoning

Likely false positives: VPN retries, mobile mail clients, cached credentials, and users fixing a mistyped password. Falcon event names and normalized fields differ by data source and tenant; verify them before deployment and tune only with an owner, scope, and review date.

Week 6 · Day 5

Python: sort and detect sequences

Page 6 / 8

What should be done

Save the Day 1 lines as events.jsonl. The program sorts the events, stores recent failure times by account + source, and prints each matching sequence once.

Easy reading plan

  1. Load each JSON line.
  2. Sort by timestamp.
  3. Remove failures older than ten minutes.
  4. Add a failure or test a success.
  5. Print S1 and S2.

Python answer

import json
from datetime import datetime, timedelta

WINDOW = timedelta(minutes=10)
UNUSUAL_TYPES = {"Network", "RemoteInteractive"}

with open("events.jsonl", encoding="utf-8") as file:
    events = [json.loads(line) for line in file if line.strip()]

events.sort(key=lambda event: event["timestamp"])
failures = {}
printed = set()

for event in events:
    now = datetime.fromisoformat(event["timestamp"].replace("Z", "+00:00"))
    key = (event["account"].lower(), event["source"].lower())
    recent = failures.get(key, [])
    recent = [time for time in recent if now - time <= WINDOW]

    if event["result"] == "failure":
        recent.append(now)
        failures[key] = recent
        continue

    if len(recent) >= 3 and event["logon_type"] in UNUSUAL_TYPES:
        sequence = event["sequence_id"]
        if sequence not in printed:
            print(sequence, "failure → success")
            printed.add(sequence)

    failures.pop(key, None)

Week 6 · Day 6

Go: small failure counter with expiry

Page 7 / 8

What should be done

Read the same time-ordered JSONL one line at a time. Keep one small state value for each account + source. Reset the counter when its ten-minute window expires or after a success.

Important input rule

This beginner version expects events.jsonl to be sorted by timestamp, as the supplied file is. Day 5 shows how to sort when order is not guaranteed.

Expected output: S1 and S2 only.

Go answer

package main

import (
    "bufio"
    "encoding/json"
    "fmt"
    "os"
    "strings"
    "time"
)

type Event struct {
    SequenceID string `json:"sequence_id"`
    Timestamp  string `json:"timestamp"`
    Account    string `json:"account"`
    Source     string `json:"source"`
    Result     string `json:"result"`
    LogonType  string `json:"logon_type"`
}

type State struct {
    Count int
    Start time.Time
}

func main() {
    file, err := os.Open("events.jsonl")
    if err != nil {
        fmt.Println("open error:", err)
        return
    }
    defer file.Close()

    states := map[string]State{}
    printed := map[string]bool{}
    scanner := bufio.NewScanner(file)

    for scanner.Scan() {
        var event Event
        if json.Unmarshal(scanner.Bytes(), &event) != nil {
            continue
        }

        now, err := time.Parse(time.RFC3339, event.Timestamp)
        if err != nil {
            continue
        }

        key := strings.ToLower(event.Account + "|" + event.Source)
        state := states[key]

        if event.Result == "failure" {
            if state.Count == 0 || now.Sub(state.Start) > 10*time.Minute {
                state = State{Count: 1, Start: now}
            } else {
                state.Count++
            }
            states[key] = state
            continue
        }

        unusual := event.LogonType == "Network" || event.LogonType == "RemoteInteractive"
        fresh := state.Count > 0 && now.Sub(state.Start) <= 10*time.Minute

        if state.Count >= 3 && fresh && unusual && !printed[event.SequenceID] {
            fmt.Println(event.SequenceID, "failure → success")
            printed[event.SequenceID] = true
        }
        delete(states, key)
    }
}

Analyst note

This version intentionally stays small. A later production version should report malformed lines, check scanner.Err(), expire inactive map entries even when no success arrives, and use a queue of timestamps for a precise sliding window.

Analyst reasoning: false positives

Corrected passwords

A user may mistype a password several times and then succeed. Check whether the source device and Interactive logon type are normal.

Mobile and cached secrets

Mail clients and cached credentials can retry an old secret. Check the client, managed-device state, and whether the failures stop after a password change.

VPN retries

Gateways can repeat authentication or change egress source. Confirm VPN session IDs, MFA result, account history, and the destination reached after success.
