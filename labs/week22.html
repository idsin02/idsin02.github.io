Week 22 Â· Day 2

KQL behavior query + tuning

Page 3 / 8

What should be done

  1. Normalize success and failure values.
  2. Anchor the hunt on each success.
  3. Join prior failures for the same source and username.
  4. Keep failures inside ten minutes.
  5. Require at least four and exclude reviewed sources.

Tuning rule

The example excludes only 10.10.0.10 (managed bastion) and 10.20.4.15 (known backup automation). Keep an owner, reason, and expiry date outside the query.

Do not allowlist an entire subnet or username just because one source is noisy.

KQL answer

Lab schema: LinuxAuthLogs(Timestamp, Source, Username, Result, Method). Rename fields for your connector before testing.

let Window = 10m;
let Threshold = 4;
let TunedSources = dynamic(["10.10.0.10", "10.20.4.15"]);
let Base = LinuxAuthLogs
| where Timestamp > ago(7d)
| where Result in~ ("failure", "success")
| where Source !in (TunedSources)
| project Timestamp, Source, Username, Result, Method;
let Successes = Base
| where Result =~ "success"
| project Source, Username, SuccessTime=Timestamp, SuccessMethod=Method;
Base
| where Result =~ "failure"
| project Source, Username, FailureTime=Timestamp, FailureMethod=Method
| join kind=inner Successes on Source, Username
| where FailureTime >= SuccessTime - Window and FailureTime < SuccessTime
| summarize FailureCount=count(),
            FirstFailure=min(FailureTime),
            LastFailure=max(FailureTime),
            FailureMethods=make_set(FailureMethod)
  by Source, Username, SuccessTime, SuccessMethod
| where FailureCount >= Threshold
| project SuccessTime, Source, Username, FailureCount,
          FirstFailure, LastFailure, FailureMethods, SuccessMethod
| order by SuccessTime desc

Analyst reasoning

Likely false positives: users mistyping passwords, automation retrying after rotated keys, and bastion hosts retrying delegated logins. Check whether the exact source is managed, whether the method changed from password to public key, whether the account is privileged, and what commands or child processes followed the successful login.

CrowdStrike CQL answer

Confirm parser and field names with one known SSH failure and success before running the sequence query.

#event.dataset="linux.auth" service="sshd"
| in(event.outcome, values=["failure", "success"])
| !in(source.ip, values=["10.10.0.10", "10.20.4.15"])
| head(limit=20000)
| groupBy([source.ip, user.name], function=slidingTimeWindow([
    { event.outcome="failure" | count(as=FailureCount) },
    selectLast([event.outcome, auth.method, @timestamp])
  ], span=10m), limit=max)
| FailureCount >= 4
| event.outcome="success"
| rename(field="@timestamp", as="SuccessTime")
| table([SuccessTime, source.ip, user.name, FailureCount, auth.method])

Analyst reasoning

Likely false positives: users mistyping passwords, automation using a stale or rotated key, and bastion retry behavior. The query follows the ordered-window pattern, but parser mappings vary by Falcon tenant; verify the event set, ordering, time picker, and field map with local data.

Week 22 Â· Day 5

Simple Python sequence finder

Page 6 / 8

What should be done

Save the Day 1 JSONL as events.jsonl. The script keeps recent failure times for each source and username, removes old entries, and prints an arrow only when a non-tuned success reaches the threshold.

Easy reading plan

  1. Read one JSON object.
  2. Create a source + username key.
  3. Discard failures older than ten minutes.
  4. Add failures to the key.
  5. On success, alert at four or more.

Python answer

import json
from collections import defaultdict
from datetime import datetime, timedelta

WINDOW = timedelta(minutes=10)
THRESHOLD = 4
TUNED_SOURCES = {"10.10.0.10", "10.20.4.15"}
failures = defaultdict(list)

with open("events.jsonl", encoding="utf-8") as file:
    for line in file:
        event = json.loads(line)
        now = datetime.fromisoformat(event["timestamp"].replace("Z", "+00:00"))
        key = (event["source"], event["username"])

        failures[key] = [
            seen for seen in failures[key]
            if now - seen <= WINDOW
        ]

        if event["result"] == "failure":
            failures[key].append(now)
        elif (
            event["result"] == "success"
            and event["source"] not in TUNED_SOURCES
            and len(failures[key]) >= THRESHOLD
        ):
            print(
                f'{event["case_id"]}: {event["source"]} / '
                f'{event["username"]} â†’ {len(failures[key])} failures then success'
            )

Go windowed counters

What should be done

Read the same JSONL stream. A map stores recent failure timestamps for each source and username. Each new event prunes the key's window before the counter is checked.

Go answer

package main

import (
    "bufio"
    "encoding/json"
    "fmt"
    "os"
    "time"
)

type Event struct {
    CaseID    string `json:"case_id"`
    Timestamp string `json:"timestamp"`
    Source    string `json:"source"`
    Username  string `json:"username"`
    Result    string `json:"result"`
}

func main() {
    file, _ := os.Open("events.jsonl")
    defer file.Close()

    const threshold = 4
    window := 10 * time.Minute
    tuned := map[string]bool{"10.10.0.10": true, "10.20.4.15": true}
    failures := map[string][]time.Time{}
    scanner := bufio.NewScanner(file)

    for scanner.Scan() {
        var event Event
        json.Unmarshal(scanner.Bytes(), &event)
        now, _ := time.Parse(time.RFC3339, event.Timestamp)
        key := event.Source + "|" + event.Username

        recent := []time.Time{}
        for _, seen := range failures[key] {
            if now.Sub(seen) <= window {
                recent = append(recent, seen)
            }
        }
        failures[key] = recent

        if event.Result == "failure" {
            failures[key] = append(failures[key], now)
        } else if event.Result == "success" && !tuned[event.Source] && len(failures[key]) >= threshold {
            fmt.Printf("%s: %s / %s â†’ %d failures then success\n",
                event.CaseID, event.Source, event.Username, len(failures[key]))
        }
    }
}

Analyst note

The example stays intentionally small. Production code should handle file, JSON, timestamp, and scanner errors; bound map growth; decide whether to reset counters after success; and attach an alert identifier. The learning goal here is the source/user key and time-window behavior.
