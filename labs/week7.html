Week 7 · Day 1

Understand the account events

Page 2 / 8

What should be done

Start with Windows Security event 4720 for account creation and event 4732 for a member added to a local security group. Join on device plus target account SID; require local Administrators SID S-1-5-32-544.

Why SID matching matters

Names can be renamed or localized. The built-in Administrators SID is stable, and the new account SID connects creation to group addition.

Easy rule: same device + same target SID + 4720 then 4732 + Administrators SID + no approved tuple.

Week 7 · Day 2

KQL behavior query + tuning

Page 3 / 8

What should be done

  1. Build a 4720 account-creation set.
  2. Build a 4732 local-Administrators set.
  3. Join by device and account SID.
  4. Keep additions within ten minutes.
  5. Remove exact approved changes.

Tuning rule

Use a small approved-change table keyed by Actor, NewAccount, and Device. In production, populate it from reviewed change-management data and expire old entries.

Never suppress all activity from an imaging or provisioning actor; a compromised service identity can still be abused.

KQL answer

Paste into Microsoft Defender Advanced Hunting or Microsoft Sentinel after confirming the SecurityEvent schema and local-group field mapping.

let Window = 10m;
let ApprovedChanges = datatable(Actor:string, NewAccount:string, Device:string)
[
  "CORP\\svc_imaging",      "local_build",    "ENG-IMG-221",
  "CORP\\svc_breakglass",   "bg-local-01",    "DC-OPS-02",
  "CORP\\svc_provisioning", "helpdesk_local", "HR-KIOSK-07"
];
let Created = SecurityEvent
| where EventID == 4720
| extend Actor = strcat(SubjectDomainName, "\\", SubjectUserName)
| project CreateTime=TimeGenerated, Device=Computer, Actor,
          NewAccount=TargetUserName, AccountSid=TargetSid;
let AddedToAdmins = SecurityEvent
| where EventID == 4732
| where TargetSid == "S-1-5-32-544" or TargetAccount =~ "Administrators"
| extend Actor = strcat(SubjectDomainName, "\\", SubjectUserName)
| project AddTime=TimeGenerated, Device=Computer, Actor,
          NewAccount=tostring(split(MemberName, "\\")[-1]),
          AccountSid=MemberSid, TargetGroup=TargetAccount;
Created
| join kind=inner AddedToAdmins on Device, AccountSid
| where AddTime between (CreateTime .. CreateTime + Window)
| project Actor=Actor1, NewAccount=NewAccount1, TargetGroup,
          Device, CreateTime, AddTime
| join kind=leftanti ApprovedChanges on Actor, NewAccount, Device
| order by AddTime desc

Analyst reasoning

False positives: approved imaging, emergency break-glass setup, and IT provisioning may be legitimate. Verify the actor, ticket, device scope, account naming standard, creation time, and whether the local account later logs on remotely.

CrowdStrike CQL answer

Confirm the event names and fields with one known account-change record. The lookup CSV must contain actor,new_account,device,approved.

#event_simpleName=/^(UserAccountCreated|UserAccountAddedToGroup)$/
| case {
    #event_simpleName="UserAccountCreated" | step:="created";
    #event_simpleName="UserAccountAddedToGroup" GroupSid="S-1-5-32-544" | step:="admin_added";
    * | step:="other";
  }
| step!="other"
| match(file="approved_local_admin_changes.csv",
        field=[UserName, TargetUserName, ComputerName],
        column=[actor, new_account, device],
        include=[approved], strict=false)
| default(value="false", field=[approved])
| approved!="true"
| groupBy([ComputerName, TargetUserSid], function=[
    collect([#event_simpleName, @timestamp, UserName, TargetUserName, GroupName]),
    count(step, distinct=true, as=step_count),
    min(@timestamp, as=first_seen),
    max(@timestamp, as=last_seen)
  ])
| step_count=2
| elapsed_ms:=last_seen-first_seen
| elapsed_ms<=600000
| table([UserName, TargetUserName, GroupName, ComputerName, first_seen, last_seen])

Analyst reasoning

False positives: imaging, break-glass, and provisioning activity should be checked against an approved lookup. Parser names vary, so first prove the mapping with known events; a missing field must not silently turn into a broad exclusion.

Week 7 · Day 5

Simple Python correlation

Page 6 / 8

What should be done

Save Day 1 as events.jsonl. The script remembers each 4720 by device and account SID. When it sees a 4732 to Administrators, it checks time and the exact allowlist tuple.

Expected output

CORP\jsmith → audit_temp → Administrators → FIN-WS-014
CORP\lpatel → svc_backup_local → Administrators → DB-SRV-03

Python answer

import json
from datetime import datetime

ADMIN_SID = "S-1-5-32-544"
WINDOW_SECONDS = 10 * 60
ALLOWLIST = {
    ("CORP\\svc_imaging", "local_build", "ENG-IMG-221"),
    ("CORP\\svc_breakglass", "bg-local-01", "DC-OPS-02"),
    ("CORP\\svc_provisioning", "helpdesk_local", "HR-KIOSK-07"),
}

def time_of(event):
    return datetime.fromisoformat(event["timestamp"].replace("Z", "+00:00"))

created = {}
with open("events.jsonl", encoding="utf-8") as file:
    events = [json.loads(line) for line in file]

for event in sorted(events, key=time_of):
    key = (event["device"], event["target_sid"])

    if event["event_id"] == 4720:
        created[key] = event
        continue

    approved = (event["actor"], event["target_account"], event["device"]) in ALLOWLIST
    first = created.get(key)
    if event["event_id"] == 4732 and event["group_sid"] == ADMIN_SID and first:
        seconds = (time_of(event) - time_of(first)).total_seconds()
        if 0 <= seconds <= WINDOW_SECONDS and not approved:
            print(f'{event["actor"]} → {event["target_account"]} → '
                  f'{event["target_group"]} → {event["device"]}')

Analyst reasoning

False positives: a legitimate image, break-glass procedure, or provisioning run can print the same chain unless its exact actor + account + device tuple is approved. Review and expire allowlist entries; do not trust an account name alone.

Week 7 · Day 6

Go per-device change report

Page 7 / 8

What should be done

Read the same JSONL line by line. Correlate creation and privileged group-add events, then group detected account names by device. This keeps the report small and useful.

Expected report

FIN-WS-014: 1 privileged change(s) → [audit_temp]
DB-SRV-03: 1 privileged change(s) → [svc_backup_local]

Go map order can place the two lines in either order.

Go answer

package main

import (
    "bufio"
    "encoding/json"
    "fmt"
    "os"
    "time"
)

type Event struct {
    Time    string `json:"timestamp"`
    ID      int    `json:"event_id"`
    Device  string `json:"device"`
    Actor   string `json:"actor"`
    Account string `json:"target_account"`
    SID     string `json:"target_sid"`
    Group   string `json:"target_group"`
    GroupSID string `json:"group_sid"`
}

func main() {
    file, _ := os.Open("events.jsonl")
    defer file.Close()

    created := map[string]Event{}
    report := map[string][]string{}
    approved := map[string]bool{
        "CORP\\svc_imaging|local_build|ENG-IMG-221": true,
        "CORP\\svc_breakglass|bg-local-01|DC-OPS-02": true,
        "CORP\\svc_provisioning|helpdesk_local|HR-KIOSK-07": true,
    }

    scan := bufio.NewScanner(file)
    for scan.Scan() {
        var e Event
        json.Unmarshal(scan.Bytes(), &e)
        key := e.Device + "|" + e.SID

        if e.ID == 4720 {
            created[key] = e
            continue
        }

        first, found := created[key]
        allowKey := e.Actor + "|" + e.Account + "|" + e.Device
        if e.ID == 4732 && e.GroupSID == "S-1-5-32-544" && found && !approved[allowKey] {
            start, _ := time.Parse(time.RFC3339, first.Time)
            end, _ := time.Parse(time.RFC3339, e.Time)
            if end.Sub(start) >= 0 && end.Sub(start) <= 10*time.Minute {
                report[e.Device] = append(report[e.Device], e.Account)
            }
        }
    }

    for device, accounts := range report {
        fmt.Printf("%s: %d privileged change(s) → %v\n", device, len(accounts), accounts)
    }
}

Analyst reasoning

False positives: imaging, break-glass, and provisioning cases can inflate a per-device report. Apply the same exact allowlist before counting so approved changes do not hide a separate unapproved account on the same device.

Capstone: prove the privileged change

Full hunt checklist

  1. Find event 4720 and record actor, new account, account SID, device, and time.
  2. Find event 4732 on the same device and account SID.
  3. Require target group SID S-1-5-32-544.
  4. Require the group-add within ten minutes after creation.
  5. Compare actor + new account + device with the approved-change allowlist.
  6. Show both matching cases and prove all benign cases stay quiet.

Approved-change allowlist logic

An event is approved only when all three fields match an active entry:

actor + new account + device

svc_imaging + local_build + ENG-IMG-221
svc_breakglass + bg-local-01 + DC-OPS-02
svc_provisioning + helpdesk_local + HR-KIOSK-07

A ticket or tool name is supporting evidence, not a safe wildcard by itself.
