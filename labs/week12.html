Week 12 · Day 2

KQL behavior query + tuning

Page 3 / 8

Build the behavior in four steps

  1. Read DeviceProcessEvents.
  2. Keep the WMI provider parent.
  3. Keep PowerShell, pwsh, or cmd children.
  4. Require a suspicious command-line clue, then apply narrow approved-context filters.

Why narrow tuning matters

Do not exclude every event from an administrator or every WMI-launched shell. Tie an exception to at least two stable facts, such as an approved actor plus an exact script path.

Give production allowlists an owner, business reason, review date, and expiry date.

KQL answer

Validation place: Microsoft Defender Advanced Hunting. Confirm field availability and replace example approved context with tenant-owned values before production use.

DeviceProcessEvents
| where InitiatingProcessFileName =~ "WmiPrvSE.exe"
| where FileName in~ ("powershell.exe", "pwsh.exe", "cmd.exe")
| where ProcessCommandLine has_any (
    "EncodedCommand", "whoami", "DownloadString",
    "Invoke-WebRequest", "FromBase64String"
  )
  or ProcessCommandLine contains " -enc "
  or ProcessCommandLine contains "-WindowStyle Hidden"
  or ProcessCommandLine contains " -w hidden"
  or ProcessCommandLine contains "-ExecutionPolicy Bypass"
  or ProcessCommandLine contains " -ep bypass"
  or ProcessCommandLine contains @"\Users\Public\"
| where not(
    AccountName =~ "svc_sccm"
    and ProcessCommandLine has @"C:\ProgramData\Microsoft\CCM\Scripts\Inventory.ps1"
  )
| where not(
    AccountName =~ "svc_monitor"
    and ProcessCommandLine has @"C:\Program Files\MonitoringAgent\collect.cmd"
  )
| extend RemoteSource = coalesce(
    column_ifexists("InitiatingProcessRemoteSessionIP", ""),
    "not_recorded"
  )
| project Timestamp, DeviceName, AccountName, RemoteSource,
          InitiatingProcessFileName, FileName, ProcessCommandLine
| order by Timestamp desc

Analyst reasoning and false positives

Likely false positives: SCCM or another software-deployment platform, monitoring products that launch health checks, inventory scripts, and approved remote administration. Verify the actor or service account, exact command, script path, source address, device group, owner, schedule, and change ticket. A common product name alone is not enough to close the alert.

Analyst reasoning and false positives

Likely false positives: Falcon-observed SCCM execution, monitoring-agent collection commands, inventory automation, and approved help-desk remote actions. Check whether the actor, command, source, target device, and execution time all match the documented workflow. If RemoteAddressIP4 is absent, keep the event and record that the remote source is unavailable rather than treating absence as benign.

Likely false positives: SCCM task execution, monitoring-product health collection, inventory scripts, and approved remote administration. The Sigma filters are deliberately paired conditions. Python answer

Run locally: python wmi_classifier.py events.jsonl

import json
import sys

SHELLS = {"powershell.exe", "pwsh.exe", "cmd.exe"}
SUSPICIOUS = (
    "-encodedcommand", " -enc ", "-windowstyle hidden", " -w hidden",
    "-executionpolicy bypass", " -ep bypass", "whoami", "downloadstring",
    "invoke-webrequest", "frombase64string", "\\users\\public\\",
)

def base_name(path):
    return path.replace("/", "\\").lower().rsplit("\\", 1)[-1]

def is_approved(event, command):
    actor = event.get("actor", "").lower()
    return (
        actor.endswith("\\svc_sccm")
        and "\\programdata\\microsoft\\ccm\\scripts\\inventory.ps1" in command
    ) or (
        actor.endswith("\\svc_monitor")
        and "\\program files\\monitoringagent\\collect.cmd" in command
    )

def is_wmi_shell(event):
    parent = base_name(event.get("parent_image", ""))
    child = base_name(event.get("child_image", ""))
    command = event.get("command_line", "").lower()
    suspicious = any(term in command for term in SUSPICIOUS)
    return (
        parent == "wmiprvse.exe"
        and child in SHELLS
        and suspicious
        and not is_approved(event, command)
    )

def main(path):
    correct = 0
    total = 0
    with open(path, encoding="utf-8") as handle:
        for line in handle:
            if not line.strip():
                continue
            event = json.loads(line)
            matched = is_wmi_shell(event)
            verdict = "MATCH" if matched else "NO MATCH"
            print(f"{event['event_id']}: {verdict} → {event['device']}")
            correct += matched == (event["expected"] == "TP")
            total += 1
    print(f"Validation: {correct}/{total} correct")

if __name__ == "__main__":
    main(sys.argv[1] if len(sys.argv) > 1 else "events.jsonl")

Why this stays simple

The classifier uses one function per idea: get a base name, check approved context, then check the detection behavior. It streams the file line by line and does not need third-party packages.

Go answer

Run locally: go run wmi_counter.go events.jsonl

package main

import (
    "bufio"
    "encoding/json"
    "fmt"
    "os"
    "path/filepath"
    "sort"
    "strings"
)

type Event struct {
    EventID    string `json:"event_id"`
    Device     string `json:"device"`
    Actor      string `json:"actor"`
    Parent     string `json:"parent_image"`
    Child      string `json:"child_image"`
    Command    string `json:"command_line"`
}

var suspicious = []string{
    "-encodedcommand", " -enc ", "-windowstyle hidden", " -w hidden",
    "-executionpolicy bypass", " -ep bypass", "whoami", "downloadstring",
    "invoke-webrequest", "frombase64string", `\users\public\`,
}

func approved(e Event, command string) bool {
    actor := strings.ToLower(e.Actor)
    return (strings.HasSuffix(actor, `\svc_sccm`) &&
        strings.Contains(command, `\programdata\microsoft\ccm\scripts\inventory.ps1`)) ||
        (strings.HasSuffix(actor, `\svc_monitor`) &&
        strings.Contains(command, `\program files\monitoringagent\collect.cmd`))
}

func isWMIShell(e Event) bool {
    parent := strings.ToLower(filepath.Base(strings.ReplaceAll(e.Parent, `\`, `/`)))
    child := strings.ToLower(filepath.Base(strings.ReplaceAll(e.Child, `\`, `/`)))
    command := strings.ToLower(e.Command)
    shell := child == "powershell.exe" || child == "pwsh.exe" || child == "cmd.exe"
    hasClue := false
    for _, term := range suspicious {
        if strings.Contains(command, term) {
            hasClue = true
            break
        }
    }
    return parent == "wmiprvse.exe" && shell && hasClue && !approved(e, command)
}

func main() {
    path := "events.jsonl"
    if len(os.Args) > 1 {
        path = os.Args[1]
    }
    file, err := os.Open(path)
    if err != nil {
        fmt.Fprintln(os.Stderr, err)
        os.Exit(1)
    }
    defer file.Close()

    counts := map[string]int{}
    scanner := bufio.NewScanner(file)
    for scanner.Scan() {
        var event Event
        if err := json.Unmarshal(scanner.Bytes(), &event); err != nil {
            fmt.Fprintln(os.Stderr, "bad JSONL:", err)
            os.Exit(1)
        }
        if isWMIShell(event) {
            counts[event.Device+" | "+event.Actor]++
        }
    }
    if err := scanner.Err(); err != nil {
        fmt.Fprintln(os.Stderr, err)
        os.Exit(1)
    }

    keys := make([]string, 0, len(counts))
    for key := range counts {
        keys = append(keys, key)
    }
    sort.Strings(keys)
    for _, key := range keys {
        fmt.Printf("%s → %d\n", key, counts[key])
    }
}

No YARA this week

YARA is useful for matching file content or memory patterns. This detection is driven by process ancestry and command-line context, so adding a YARA rule would distract from the primary signal.

Week 12 · Day 7

Separate management from rare execution

Page 8 / 8

Context changes the decision

Common, documented management

Actor: named service account owned by IT
Command: exact approved script in a protected path
Source: management server subnet
Timing: expected deployment or inventory window
Action: confirm and tune narrowly

Rare, high-priority WMI shell

Actor: unusual user or temporary admin
Command: encoded, hidden, bypass, discovery, or user-writable path
Source: workstation or unknown host
Timing: outside the normal window
Action: investigate process tree and remote activity

Five-question triage

  1. Is WmiPrvSE really the direct parent?
  2. Who owns the actor or service account?
  3. Is the entire command expected, not just one keyword?
  4. Is the source address part of approved administration?
  5. Is the same actor-command-device pattern common in the baseline?

Evidence to collect next

  • Full parent and child process tree
  • WMI operational logs and remote logon evidence
  • PowerShell script block or module logs, if enabled
  • DNS, network, and file activity near the event
  • Change ticket and automation owner confirmation
